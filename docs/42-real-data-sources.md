# Real Data Sources — What Is Actually Real

This chapter is the reference for data provenance in Bhu-Drishti 3D. It answers one
question precisely: **for any number the product displays, where did it come from, and
what does it not mean?**

Earlier revisions of this documentation described the system as operating on
synthetic data throughout. That is no longer accurate. The administrative gazetteer
and the building geometry are real. The land-record layer is not. Conflating the two is
the failure mode this chapter exists to prevent, so every section states its source, its
licence, its retrieval date, and its limits.

---

## 1. Provenance Classes

Every value in the product carries one of three classes. The class is surfaced in
API payloads (`provenance`, `data_provenance`, `authoritative`, `evidence_basis`) and in
the UI, not inferred by the reader.

| Class | Meaning | Examples |
| --- | --- | --- |
| **Real** | Read from a named public authority or publisher, unmodified | LGD village names and codes; Census 2011 unit counts; OSM building footprints; GlobalML footprints; AWS terrain elevation |
| **Derived** | Computed from real inputs by a documented rule | Nominatim village centroids; building massing extruded from footprint area; floor counts; FSI arithmetic; volumes; terrain interpolation |
| **Modelled** | Generated by this codebase, not evidence of anything | Parcel and plot subdivision; building and unit identifiers; ownership, ULPIN, title, mortgage and encumbrance; approvals, sanctions, violations and enforcement |

A derived value is only as trustworthy as the real inputs and the rule. A modelled
value carries no evidentiary weight regardless of how precise it looks.

## 2. Local Government Directory (LGD) — Real

### 2.1 What it is

| Field | Value |
| --- | --- |
| Publisher | Ministry of Panchayati Raj, Government of India |
| Dataset | Local Government Directory — All Villages of a State (Xls Report) |
| Source URL | `https://lgdirectory.gov.in/downloadDirectory.do` |
| Retrieved | 2026-10-01T17:35:05Z |
| Records | **677,673 villages** across **35 states and union territories** with village rows |
| Coverage | All 36 LGD state/UT entries. Chandigarh is published with no village rows. |
| Districts represented | 781 distinct district names within hierarchy |
| Sub-districts represented | 7,081 |
| Census 2011 code | Populated on 100% of rows |

The 36-entries-versus-35-states discrepancy is a property of the source, not a missing
download: Chandigarh is a single Union Territory with no revenue villages in the
directory. The API reports both figures separately (`state_entities` and
`states_with_villages`) rather than picking the flattering one.

### 2.2 How it is ingested

The export is distributed as state ZIP archives whose members are SpreadsheetML
(`.xls`) documents despite the extension. The importer is
`scripts/build_lgd_villages.py`:

- Parses SpreadsheetML XML from each `villageofSpecificState` member.
- Skips archives that are empty or malformed, recording the reason in the manifest.
- Uses `village_code` as the primary key, so duplicated state archives (Assam and
  Maharashtra are both published more than once) replace rather than double-count.
- Writes `backend/app/data/lgd_villages.sqlite` — a **gitignored build artifact**.
- Writes `backend/app/data/lgd_villages.manifest.json` — a **committed** record of
  source URL, retrieval timestamp, per-state row counts, archive sizes and SHA-256
  checksums for every input archive.

Rebuild with:

```bash
python scripts/build_lgd_villages.py --input-dir ~/Downloads --out backend/app/data/lgd_villages.sqlite
```

The SQLite file is not committed because it is 90 MB of third-party data. The manifest
is committed so that every claim in this chapter is checkable without re-downloading
anything.

### 2.3 Validation performed

- 677,673 unique `village_code` values; no duplicates survive.
- Zero rows with a blank English name.
- 100% Census 2011 code coverage.
- Cross-checked against Census 2011 official village totals. For the 31 state names that
  matched exactly, the LGD total exceeds the Census 2011 total by 24,855 rows (+3.88%).
  This is expected: LGD is a current directory, the Census is a 2011 snapshot, and
  villages have been created, merged and renamed since. The comparison is a sanity
  check on magnitude, not an attempt to reconcile the two.
- Six state names differ between LGD and the Census A-1 workbook (renames and
  transliterations). These are matched through an explicit alias table rather than by
  fuzzy string similarity.

### 2.4 What LGD is not

LGD is an **administrative directory of villages**. It is not a cadastre. It carries
**no geometry of any kind** — no polygon, no centroid, no latitude or longitude. It
says nothing about parcel boundaries, plot area, land use, ownership, title, ULPIN, or
whether any particular land is buildable.

This limit is enforced, not merely documented: `app/pipelines/lgd_villages.py` exposes
`geometry_kind: "none"` and `is_cadastre: False`, and every LGD search result is
returned with `has_focus: False`.

## 3. Census of India 2011 — Real, and kept Separate

Official A-1 workbook: hierarchy and statistics for 1 India, 35 states, 640 districts
and 5,988 sub-districts, with Census 2011 codes and village/town/household counts.

**Census 2011 and LGD are not merged.** They are different vintages with different code
systems. A village's LGD code is not its Census 2011 code. Where both are present they
are carried as separate, separately-named fields and never substituted for one another.
The counts themselves are served from a committed CSV
(`backend/app/data/census2011_admin_units.csv`) and can be queried by the code systems
they actually belong to.

## 4. Building Geometry — Real Footprints, Derived Massing

### 4.1 Microsoft GlobalML Building Footprints

Open footprint dataset, no authentication required. Returns polygon footprints.
Verified near the Airoli pilot area: **220 live footprints**.

### 4.2 OpenStreetMap (Overpass)

ODbL-licensed. Verified near the Airoli pilot area: **1,461 building ways within 400 m**,
of which **34 carry a `name` tag**.

### 4.3 The height gap, stated plainly

Neither GlobalML nor OSM supplies reliable building heights or floor counts for these
areas. Observed partitions carry `height = -1`, meaning absent. A 34-of-1,461 name
coverage rate is the honest figure: most footprints are anonymous.

**Consequence:** every 3D mass in this product is **derived**, not measured. Heights,
floor counts and volumes are computed from footprint area using documented rules. The UI
labels them as derived. Nothing in the product should be read as an as-built survey, and
no building can be measured from this data.

See [`08-3d-engine.md`](08-3d-engine.md) for the extrusion rules.

## 5. Elevation — Real

**AWS Terrain Tiles** (`s3://elevation-tiles-prod/terrarium`, terrarium-encoded global
elevation raster) backs all ground elevation. This is a real global elevation surface
and is used for terrain-aware placement and for grounding modelled geometry.

It is a coarse raster. It is not a DEM survey of a site, and it carries no structures,
vegetation or building information.

## 6. Village Coordinates — Derived, Never Asserted

LGD publishes no coordinates, so a village's map position is **derived by geocoding**
through `app/sources/nominatim.py`:

- Hierarchical query: village → sub-district → district → state, with progressive
  relaxation only while the result remains a settlement feature.
- Settlement features (village, hamlet, suburb, locality, town) are ranked above
  incidental matches — a railway station named "Airoli" is rejected in favour of the
  settlement.
- Results are cached on disk and rate-limited to roughly one request per second to
  respect the Nominatim usage policy.
- Unicode is preserved, including Devanagari combining marks.
- Unresolved villages return an **honest failure**, never a guessed coordinate.

Every geocoded response carries `authoritative: false` and a `match_quality` field. A
geocoded centroid is an approximation produced by a community data source, not a surveyed
boundary, and the product must never present it as one.

Worked example: LGD code `943726` (Airoli, Thane, Maharashtra) resolves to approximately
19.158272 N, 72.996709 E — a settlement match, consistent with but not equal to the
project's own pilot datum.

## 7. Airborne LiDAR — Unavailable, and Explained Rather Than Faked

**There is no open airborne LiDAR for India.** This was verified by auditing the
credential-free public archives, and it is a property of the available data rather than
an outage or a configuration problem:

| Source | Coverage | Reachable without credentials |
| --- | --- | --- |
| `s3://open-lidar-data` (COPC/LAZ) | BE, CH, DE, DK, EE, ES, FI, FR, IE, LU, LV, NL, PL, SE, SI, UK | Yes |
| `s3://usgs-lidar-public` (EPT/LAZ) | United States | Yes |
| `tnmaccess.nationalmap.gov` (3DEP) | United States | Yes |
| ISRO / NRSC Bhuvan | India imagery, orthoimagery, thematic layers, DEMs | Yes — but **no point clouds** |

Every precinct this product serves is in India. Therefore none of them has open LiDAR
coverage, and no environment variable changes that.

`laspy` is already a dependency and COPC/LAZ decoding is not the obstacle — coverage is.

**What the product serves instead,** each labelled accordingly:

- Real building footprints (GlobalML, OSM).
- Real elevation (AWS Terrain Tiles).
- A **modelled** point field, explicitly marked `point_cloud_kind: "MODELLED"`,
  `data_provenance: "demo-generated"`, `authoritative: false`, built from real footprints
  and grounded on real terrain.

`app/core/lidar_coverage.py` is the single source of truth for this determination, and
the API returns the reason rather than a bare refusal. The LiDAR view being unavailable
for Indian precincts is by construction, and the UI says so.

## 8. The Modelled Layer — What Must Never Be Presented as Fact

Everything in this section is generated by this codebase. All of it is gated behind the
demo flag, and all of it is labelled `demo-generated` / `authoritative: false`.

- **Parcels, plots and their subdivisions.** Polygon geometry is procedural.
- **Identifiers.** ULPINs, 3D-ULPINs, twin codes, survey numbers and unit codes are
  minted in-process.
- **Ownership and title.** Party names, share percentages, encumbrance and mortgage
  records are invented. Liability is emitted as `MODELLED_RIGHT` / `MODELLED_PARTY`
  with `encumbrance_status: "MODELLED"`, never as a real holding.
- **Approvals and enforcement.** Sanction status, violation findings, compliance
  verdicts and case queues are demonstration states, not regulatory outcomes.
- **Status vocabulary.** `APPROVED`, `VIOLATION`, `PASS`/`EXCEEDED` describe the
  generated dataset's own bookkeeping and carry no statutory meaning.
- **Change detection.** Differencing two epochs of generated data is arithmetic. It
  cannot establish that a change was unlawful, and it emits
  `status: "Suspected change (unverified)"` with `evidence_basis: "SYNTHETIC"`.

The identifier engine deserves a specific note. A checksum match proves that an
identifier encodes the same geometry the caller supplied. It proves nothing about
authenticity, and it is not a check against any government register. The UI says
"CHECKSUM MATCHES" and says so in a sentence beneath it.

## 9. Evidence Streams

Seven evidence streams (EV-01 … EV-07) are declared in `app/api/v1/evidence.py`. **Every
one is currently `available: false`**, each carrying the specific reason it could not be
obtained, a `provenance` of "None", and a `required_to_activate` statement of what would
have to arrive.

EV-01 (GIS Cadastral Parcel Map) previously claimed Tier A survey-grade provenance from
the Maharashtra Land Records Department. No cadastre was ever obtained. That claim was
removed; the stream now states plainly that only a hand-drawn demonstration footprint
exists and that it is not a parcel boundary.

`confidence_tier` and `quality_result` are never derived from a status field. Unknown
stays unknown.

## 9.1 Serving the Footprint Sources Without Overclaiming

Footprint providers are the one part of this system that is already real and already
populated, so they carry the serving machinery: a TTL cache that persists to
`data/opendata_cache.json`, single-flight fetching per area, and a background worker that
re-pulls regions which came back without named places.

Three additions keep the cost and the claims honest:

- **Conditional responses.** `GET /opendata/area` carries a strong `ETag` derived from the
  serialised payload, not from cache bookkeeping, and answers a matching `If-None-Match`
  with `304`. The tag is stable across a cache hit, so a repeat request for unchanged
  provider data costs a status code rather than 220 buildings.
- **Sparse payloads.** `?fields=counts,labels` returns only those top-level keys.
  `region`, `area`, `source`, `provenance` and `counts` are never droppable — a response
  that cannot be traced to a provider and a place is not worth the bytes it saves. An
  unrecognised field name is reported in `unknown_fields` rather than silently dropped,
  because a typo would otherwise read as an empty area.
- **Prewarming.** `OPENDATA_PREWARM_AREAS` (or `POST /opendata/prewarm`) fetches nominated
  areas once at start-up so the first request for them is served from cache. This changes
  only *when* the fetch happens. It uses the same providers, the same cache and the same
  failure paths, so an area that cannot be fetched during warm-up is still reported as
  un-fetchable on the request path, and a failed warm-up never raises.

Preheating and caching do not upgrade a source's class. A cached OSM footprint is still
**Real, non-authoritative**; `provenance.authoritative` stays `false` and OSM attribution
stays mandatory.

## 10. Licensing

| Source | Licence / terms | Attribution obligation |
| --- | --- | --- |
| LGD | Government of India open data | Publisher and report name required |
| Census of India 2011 | Government of India open data, free to reproduce in full | Publisher attribution |
| OpenStreetMap | **ODbL** | **Share-alike and visible attribution required** — see below |
| Microsoft GlobalML | Microsoft open data terms | Publisher attribution |
| AWS Terrain Tiles | Public dataset; source is SRTM, NASA, USGS and others | Upstream attribution |
| Nominatim / OSM geocoding | ODbL, Nominatim usage policy | Rate limit and user agent required |

**OSM ODbL attribution is not optional.** Any redistribution of derived OSM data must
carry attribution and remain share-alike. Nominatim additionally requires a
rate-limited, identified user agent; this deployment uses one request per second.

## 11. Quick Reference

| Domain | Class | Source |
| --- | --- | --- |
| Village names, codes, hierarchy | **Real** | LGD (Ministry of Panchayati Raj) |
| Village population and area | **Real** | Census of India 2011 (separate codes from LGD) |
| Building footprint geometry | **Real** | Microsoft GlobalML, OpenStreetMap |
| Building names | **Real, sparse** | OSM `name` tag (34 of 1,461 in the pilot area) |
| Ground and surface elevation | **Real** | AWS Terrain Tiles |
| Village map position | **Derived** | Nominatim geocoding, `authoritative: false` |
| Building height, floors, volume | **Derived** | Extrusion rules over real footprints |
| Parcel boundaries and plots | **Modelled** | This codebase |
| Ownership, ULPIN, title | **Modelled** | This codebase |
| Approvals, violations, compliance | **Modelled** | This codebase |
| Point clouds for Indian precincts | **Modelled** | No open LiDAR exists for India |
| All evidence streams EV-01…EV-07 | **Unavailable** | Nothing obtained; reasons stated per stream |
